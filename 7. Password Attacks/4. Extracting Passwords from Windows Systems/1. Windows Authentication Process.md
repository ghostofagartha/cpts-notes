- **Kerberos**: An authentication mechanism in Windows systems
- **Local Security Authority (LSA)**: Protected subsystem that authenticates users, manages local logins, oversees all aspects of local security, provides services for translating between user names and security identifiers (SIDs)

- Local Interactive Logon is handled through the coordination of many several components:
	1. The logon user interface process (LogonUI)
	2. Credential providers
	3. The Local Security Authority Subsystem Service (LSASS)
	4. One or more authentication packages
		- Dynamic-Link Libraries (DLLs) responsible for performing authentication checks
		- **e.g**: `Msv1_0.dll` authentication package is used for non-domain-joined and interactive logins
	5. Security Accounts Manager (SAM) or Active Directory

**WinLogon**
- Trusted system process responsible for managing security-related user interactions such as:
	- Launching **LogonUI** to prompt for credentials at login
	- Handling password changes
	- Locking and unlocking the workstation
- To obtain user's credentials, it relies on credential providers installed on the system; **COM** objects implemented as DLLs
- Its the only process that intercepts login requests from the keyboard, which are sent via RPC messages from **Win32k.sys**
- **Process**
	1. At logon, it immediately launches the **LogonUI** application to present the GUI
	2. After credentials collection, WinLogon passes them to the Local Security Authority Subsystem Service (LSASS) to authenticate the user

**LSASS**
- Comprised of multiple modules and governs all authentication processes
- Located At: `%SystemRoot%\System32\Lsass.exe` in the file system
- Responsible for enforcing the local security policy, authenticating users, and forwarding security audits to the **Event Log**
- Serves as Gatekeeper in Windows-based operating systems

|**Authentication Packages**|**Description**|
|---|---|
|`Lsasrv.dll`|The LSA Server service both enforces security policies and acts as the security package manager for the LSA. The LSA contains the Negotiate function, which selects either the NTLM or Kerberos protocol after determining which protocol is to be successful.|
|`Msv1_0.dll`|Authentication package for local machine logons that don't require custom authentication.|
|`Samsrv.dll`|The Security Accounts Manager (SAM) stores local security accounts, enforces locally stored policies, and supports APIs.|
|`Kerberos.dll`|Security package loaded by the LSA for Kerberos-based authentication on a machine.|
|`Netlogon.dll`|Network-based logon service.|
|`Ntdsa.dll`|Directory System Agent (DSA) that manages the Active Directory database (ntds.dit), processes LDAP queries, and handles replication between domain controllers. Only loaded on Domain Controllers.|
- Each interactive logon session creates seperate instance of the WinLogon service
- **Graphical Identification and Authentication (GINA)**: Architecture thats loaded into the process area used by WinLogon, receives and processes the credentials and invokes the authentication interfaces via the **LSALogonUser** function

**SAM Database**
- Security Account Manager
- Database file in Windows operating systems that stores user account credentials
- Authenticates local and remote users and uses cryptographic protections to prevent unauthorized access
- User passwords are stored as hashes in the registry, in **LM** or **NTLM** hashes
- SAM file located at `%SystemRoot%\system32\config\SAM` and mounted under `HKLM\SAM`, requires **SYSTEM** level privileges
- Windows system can be assigned to either a workgroup or domain during setup. If assigned to:
	1. **A Workgroup**, it handles the SAM database locally and stores all existing users locally in this database
	2. **A Domain**, the Domain Controller (DC) must validate the credentials from the Active Directory database (**ntds.dit**), which is stored in `%SystemRoot%\ntds.dit`
- To improve security against offline cracking of the SAM database, Microsoft introduced a feature in Windows NT 4.0 called **SYSKEY (syskey.exe)**
	- When enabled, SYSKEY partially encrypts the SAM file on disk, ensuring that password hashes for all local accounts are encrypted with a system-generated key

**Credential Manager**
![[Pasted image 20260809202705.png]]
- A built-in feature of all Windows operating systems that allows users to store and manage credentials used to access network resources, websites, and applications
- Credentials are stored in the user's **Credential Locker**
- Credentials encrypted and stored at: `C:\Users\[Username]\AppData\Local\Microsoft\[Vault/Credentials]\`

**NTDS**
- In Domain controlled Windows systems, logon requests are sent to Domain Controllers within the same Active Directory forest
- Each Domain Controller hosts a file called **NTDS.dit**, which is synchronized across all Domain Controllers except **Read-Only Domain Controllers (RODCs)**
- **NTDS.dit**: A database file that stores Active Directory data including (but not limited to):
	- User Accounts (username & password hash)
	- Group Accounts
	- Computer Accounts
	- Group Policy Objects
